Abstract

   This document specifies a compression scheme for Datagram Transport
   Layer Security (DTLS) datagrams in Static Header Compression (SCHC).

1.  Introduction

   Datagram Transport Layer Security (DTLS) is an essential part of many
   IoT deployments.  The most common use case is a deployment of the
   Constrained Application Protocol (CoAP) over DTLS (CoAPS) [RFC7252].
   Inspired by earlier work [SCHC-DTLS-paper], this document provides a
   compression scheme for Static Header Compession (SCHC) [RFC8724].
   While a compression scheme for CoAP already exists (see [RFC8824],
   [I-D.ietf-schc-8824-update]), the CoAP header is encrypted in CoAPS
   and thus transparent to the SCHC C/D.  As such, a compression scheme
   for DTLS is needed.  Inner CoAP header could also be compressed,
   however, this is out of scope of this document.

3.  DTLS compression

   This section defines DTLS fields that can be compressed with SCHC.
   [SCHC-DTLS-paper] describes a rigid compression scheme that only
   allows for one configuration of DTLS 1.2 [RFC6347] header
   compression.  This specification tries aims for a broader compression
   that also allows for compression of DTLS 1.3 headers which differ
   from DTLS 1.2 headers [RFC9147].  Older versions of DTLS are not
   supported.

3.1.  Record Layer

   [RFC6347], [RFC9147], and [RFC9846] defines the format of DTLS
   packets in the presentation language defined in [RFC9846], starting
   from the DTLS record layer.  Multiple DTLS records may be put into a
   single datagrame.  However, for the purposes of SCHC it is
   RECOMMENDED, to have one record per datagram.  Otherwise, fitting one
   packet type into a single group might not become difficult.  Some
   fields mentioned in [RFC9147] for the record layer are either
   described in [RFC6347] or [RFC9846].  The fields of the DTLS record
   layer are as follows, we cite the appropriate document of its
   definition below.

   *  type: An 8-bit field that encodes the higher-level protocol used
      to process the enclosed fragment.  Its values are assigned by IANA
      in the TLS ContentType registry as per [RFC9846].

   *  version: A 16-bit field that defines the version of the DTLS
      protocol.  It MUST be set to {254, 253} for both DTLS 1.2
      [RFC6347] and DTLS 1.3 (where it is included for legacy purposes)
      except for the initial ClientHello with DTLS 1.3 where it also may
      be {254, 255} for compatibility purposes [RFC9147].

   *  epoch: A 16-bit field that is a counter of cipher state changes in
      DTLS 1.2 [RFC6347] and the least significant 2 bytes of the
      connection epoch value in DTLS 1.3 [RFC9147].

   *  sequence_number: A 48-bit filed that is the sequence number for
      the given record [RFC6347].

   *  length: A 16-bit field that is the length (in bytes) of the
      following fragment.  The length MUST NOT exceed 2¹⁴ bytes
      [RFC9846].

   *  fragment: The data of length length being transmitted.  This value
      is transparent and is treated as an independent block to be dealt
      with by the higher-level protocol specified by the type field.  If
      compression applies, it is specified in the following [RFC9846].

   All fields but fragment can be covered by SCHC compression rules with
   the appropriate field lengths.  Since the compression of the fragment
   field is dependent on type, however, it is not possible to create one
   rule for all DTLS records.  The fields of fragment are specified in
   the following sections If another record follows fragment it should
   be made clear using _var_ length of a payload field within fragment.
